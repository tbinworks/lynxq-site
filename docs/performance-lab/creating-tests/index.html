Creating performance tests

1. Choose the target

Section titled “1. Choose the target”

Select a saved request… opens a dropdown under the Target bar that lists saved requests by collection. Type to search names, methods, URLs and collections. Each row shows the method, the name and the URL. Collections are groups to browse, not targets.

The choice is kept by the request's id, so renaming the request or switching tabs does not change it. The test uses the request as saved when it starts, with what it inherits from its folders and collection. A read-only bar shows its protocol, method and URL, and the heading says where it is kept (Target — Shop API / List products).

2. Configure the load

Section titled “2. Configure the load”
Setting Default Range Meaning
Virtual users 10 1–500 Concurrent workers; each has one request in flight at a time.
Duration 30 s 1–3600 s Seconds the test runs.
Ramp-up 5 s 0 to the duration Seconds over which the users start, evenly.
Limit request rate On, 20/s 1–5,000 requests/s Requests started per second, across all users together.
Measure to Full response Full response, Headers only See below
Run checks On On, Off Run the request's checks (and scripts) on each response

The environment is the one active when the test starts. The test uses a copy of it, and never switches or writes it.

Execution model

Section titled “Execution model”
  • A virtual user is a lightweight task, not a thread. It sends its request in a loop, one at a time, until the test ends.
  • Concurrency (virtual users) limits how many requests are in flight immediately. Rate limits how many may start each second. Both apply.
  • Ramp-up: user i of n starts at ramp × i / n, so all users are running when ramp-up ends.
  • The rate cap is global: one limiter shared by all users. A user waits for its turn before sending, so requests never pile up in a queue.
  • No retries, for any method.
  • Redirects are not followed: a 3xx counts as the response, so no request leaves the confirmed hosts.
  • Built-in variables ({{$uuid}} …) are resolved for each request. Values a request extracts are kept for that user only.

Measurement

Section titled “Measurement”
Option Total time ends at Notes
Full response The end of the body: full-response latency. Default
Headers only The response headers; the body is not read (body checks will not run). The connection is closed rather than reused afterwards, so latency differs from a full-response test

Checks and scripts

Section titled “Checks and scripts”

With Run checks on, each response's checks run. When checks need the body, at most 64 KB of it is kept for that one request. Before scripts run on every request (on a pool of their own). After scripts run with the checks. Scripts read bodies up to 16 MB, kept per user. Scripts run only if the workspace's scripts are on and approved.

3. Save as a scenario

Section titled “3. Save as a scenario”

Save scenario keeps the target and settings as a scenario in the workspace (lab/<name>.lab.toml), listed in the Performance side panel. Revert goes back to the saved scenario. The panel supports +, Rename (F2), Duplicate (Ctrl+D) and Delete with Undo, like the other panels. Scenario: New in the palette creates one.

A scenario from an earlier version whose target was a collection or an unsaved request cannot be tested: Choose a saved request.
